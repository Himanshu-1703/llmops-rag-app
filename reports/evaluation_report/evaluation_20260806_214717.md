<details><summary><b>View Test Case Data</b></summary>

- **Input:** How do ML systems and LLM apps differ in determinism, dynamic cost, and input-output tracking?
- **Actual Output:** - Determinism
  - ML systems: deterministic — same input gives the same output (easy pass/fail testing). Evaluation can be cheap and automated with mathematical checks.
  - LLM apps: probabilistic and non-deterministic — the same input can produce different, but valid, outputs. Outputs are semantically flexible (not exact strings), so there is no single correct answer and simple assertion tests fail.

- Dynamic cost
  - ML systems: cost is stable and predictable (example: 100 rows → cost 10 rupees).
  - LLM apps: cost is dynamic and hard to fix because both input length and output length affect cost (you pay for input and output tokens).

- Input–output tracking
  - ML systems: input→output relationship is fixed and easy to track.
  - LLM apps: relationship is dynamic and must be managed; outputs change over time and require human judgment or detailed text reports for evaluation. Multiple components (e.g., retriever and generator) can fail independently, and human annotation for evaluation is costly and does not scale.
- **Expected Output:** ML systems are generally deterministic: the same input row gives the same output every time, with fixed compute/cost for that input size.  

LLM apps are probabilistic and dynamic: the same input can produce different outputs, and both cost and compute vary because input length, output length, and retrieved context all change.  

Also, ML prediction usually has a simple input-to-output flow, while LLM apps often require tracking the full journey from input through retrieval, prompting, and output.

</details>

- **Input:** How can a generator hallucinate despite correct retrieval, and what causes it?
- **Actual Output:** How it can hallucinate despite correct retrieval
- The generator can ignore or not use the retrieved context, and produce answers that are not grounded in those documents.
- It can invent facts or details not present in the context, so the output is wrong even though retrieval was correct.
- It may return results in the wrong format or style you expect, making the output effectively incorrect for your application.

What causes this
- The generator (LLM) itself hallucinating or failing to follow the provided context/instructions.
- Prompt injection inside the retrieved content — malicious or misleading text in documents that causes the model to follow wrong instructions or reveal unwanted content (jailbreaks).
- Mismatch between what you expect (format, specificity) and what the generator was prompted or set up to produce.
- In agentic/autonomous setups, silent interpretation failures where the model’s hallucination is not obvious or detectable by downstream checks.
- **Expected Output:** A generator can hallucinate even when retrieval is correct by ignoring the retrieved context and producing an answer from its own assumptions or from unrelated parts of the context. This happens because the retriever may fetch the right documents, but the generator can still misread them, over-prioritize certain text, or add unsupported facts.

## ✅ PASS - test_case_12

<details><summary><b>View Test Case Data</b></summary>

- **Input:** How do LLM evals differ from software tests in fixed vs. flexible output and multi-metric quality?
- **Actual Output:** - Fixed vs flexible output
  - Traditional software: outputs are fixed and deterministic. Given the same input you expect one exact output (e.g., 2+3 = 5). Tests are simple assertions that either pass or fail.
  - LLMs: outputs are flexible and probabilistic. The same prompt can yield very different but valid answers (different words, length, structure). Exact-string checks break down because many different outputs can be correct or acceptable.

- Multi-metric quality vs single correctness
  - Traditional software testing measures a single correctness dimension: does the program produce the expected exact result?
  - LLM evaluation is multi-dimensional. You must judge correctness, relevance, completeness, groundedness (is the answer based on your data or hallucinated), etc. An output can be correct in one sense but fail another (right fact but irrelevant or incomplete).
  - Complex systems have multiple components (e.g., retriever and generator) that can fail independently, so you must evaluate components and end-to-end behavior.

- Practical consequences
  - Simple assertion-based testing is often impossible for LLMs. Evaluation requires human judgment and detailed reports, which is costly and hard to scale, pushing towards automated but more nuanced evaluation methods.
- **Expected Output:** LLM evals are harder than software tests because:

- **Software tests** usually check **fixed, deterministic output** — one input should produce one expected answer, so it’s mostly **pass/fail**.
- **LLM evals** deal with **flexible, probabilistic output** — the same prompt can produce different but still valid answers.

Also, software testing mostly checks **correctness only**, while LLM evals need **multi-metric quality checks** like:
- correctness
- relevance
- completeness
- groundedness
- safety

So, unlike software tests, LLM evals are not just about “right or wrong”; they evaluate whether the answer is good across multiple dimensions.
