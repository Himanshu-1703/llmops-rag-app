- Model evals: Not limited to a single metric — measure capabilities and behavior relevant to task fit and reliability. Summary
- Model evals = evaluate the model’s capabilities and whether it fits a task (broader testing setup). App evals = evaluate the application’s user-facing behavior and component-level performance, plus operational metrics like latency and cost.

- **Input:** How do ML systems and LLM apps differ in determinism, dynamic cost, and input-output tracking?
- **Actual Output:** - Determinism
  - ML systems: deterministic. Same input → same output (fixed labels like 1 or 0). Test cases either pass or fail; evaluation is mathematical and automated.
  - LLM apps: probabilistic and non-deterministic. The same input can produce different outputs (different words, length, phrasing). Semantic equivalence matters rather than exact text match.

- Dynamic cost
  - ML systems: cost is predictable and proportional to input size. Example from context: 100 rows always costs 10 rupees when run on the hosted model.
  - LLM apps: costs are less predictable — you have multiple components (retriever, generator/LLM) and evaluation often requires human judgment and detailed reporting, which is costly.

- Input–output tracking
  - ML systems: easier to track. Only the model is the main moving part, and fixed labels make mapping inputs to outputs straightforward.
  - LLM apps: harder to track. Multiple components and nondeterministic outputs mean you must actively manage the relationship between input and output, judge semantic correctness, and produce detailed evaluations.
- **Expected Output:** ML systems are generally deterministic: the same input row gives the same output every time, with fixed compute/cost for that input size.  

LLM apps are probabilistic and dynamic: the same input can produce different outputs, and both cost and compute vary because input length, output length, and retrieved context all change.  

Also, ML prediction usually has a simple input-to-output flow, while LLM apps often require tracking the full journey from input through retrieval, prompting, and output.

## ✅ PASS - test_case_2

<details><summary><b>View Test Case Data</b></summary>

- **Input:** How can a generator hallucinate despite correct retrieval, and what causes it?
- **Actual Output:** A generator can “hallucinate” even when retrieval looks correct because of problems in the pipeline and how the retrieved context is presented and used. From the given context, the causes are:

- Bad or mixed context: the generator depends entirely on the context you provide. If the vector store or ingestion process mixed up documents or produced a bad context, the generator will combine wrong facts (example: it pulled six weeks of data and mixed them) and output incorrect answers even while following instructions.
- Workflow-level mismatch: retriever and generator can each work fine individually, but their interaction may produce errors. The pipeline can “break” when the retrieved snippets don’t align with what the generator expects, causing incorrect outputs.
- Determinism/variance: the same inputs (augmented prompt + system prompt + context) can produce slightly different outputs on different runs, so sometimes the generator returns a wrong but plausible answer (example: returns “Amit” instead of “Rahul”).
- Instruction-context gap: control is only on the context and the system prompt. If those don’t correctly constrain or supply facts, the model may produce an answer that fits the intent but is factually wrong.

Because of these causes, you need not only retrieval and generation evals, but also a workflow-level eval that checks how retriever + generator behave together to flag such hallucinations.
- **Expected Output:** A generator can hallucinate even when retrieval is correct by ignoring the retrieved context and producing an answer from its own assumptions or from unrelated parts of the context. This happens because the retriever may fetch the right documents, but the generator can still misread them, over-prioritize certain text, or add unsupported facts.

</details>

<details><summary><b>View Test Case Data</b></summary>

- **Input:** How do LLM evals differ from software tests in fixed vs. flexible output and multi-metric quality?
- **Actual Output:** Fixed vs flexible output
- Software (fixed output) is deterministic. For the same input you expect one exact output (e.g., 2+3 must be 5). Tests are binary: the program either produces the correct result or it does not.
- LLMs (flexible output) are probabilistic. The same input can produce different but valid outputs (different wording, length, level of detail). That variability makes evaluation harder because there is no single correct string.

Multi-metric quality vs single correctness
- Software tests mostly measure correctness (pass/fail).
- LLM evals must check many dimensions, for example:
  - Correctness (is the factually right answer given?)
  - Relevance (does the answer address the asked question? e.g., asked “overfitting” but got a definition of “underfitting” — correct but irrelevant)
  - Completeness (is the answer complete?)
  - Groundedness (is the answer based on the retrieved or provided data, as in RAG, or hallucinated?)
- LLM evaluation is not just metrics. It is the whole testing setup: what you are testing, on what basis, when, and with which tools.

Practical goal
- The aim of LLM evals is to answer practical questions, such as: can the model be used for a task, is it production-ready, did a prompt change improve results, or is a RAG answer grounded — not just to produce a single score.
- **Expected Output:** LLM evals are harder than software tests because:

- **Software tests** usually check **fixed, deterministic output** — one input should produce one expected answer, so it’s mostly **pass/fail**.
- **LLM evals** deal with **flexible, probabilistic output** — the same prompt can produce different but still valid answers.

Also, software testing mostly checks **correctness only**, while LLM evals need **multi-metric quality checks** like:
- correctness
- relevance
- completeness
- groundedness
- safety

So, unlike software tests, LLM evals are not just about “right or wrong”; they evaluate whether the answer is good across multiple dimensions.
