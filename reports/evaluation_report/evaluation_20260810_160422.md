- **Input:** How do ML systems and LLM apps differ in determinism, dynamic cost, and input-output tracking?
- **Actual Output:** - Determinism
  - ML/software: deterministic — same input gives the same output every time (e.g., a regression model returns 10 for the same input; a calculator always gives 2+2=4).
  - LLM apps: probabilistic — the same input can produce different outputs on different calls (e.g., 10.5, 11, 9.5), so outputs are not fixed.

- Dynamic cost
  - ML systems: compute/cost is roughly fixed per workload (e.g., 100 rows costing X units or 10 rupees regardless of content).
  - LLM apps: compute and cost vary with the input, the generated output, and any retrieved context — cost is dynamic per request.

- Input→output tracking (workflow)
  - ML prediction: typically a single-step prediction; you usually don’t need to track the full journey from input to output for each prediction.
  - LLM apps: involve multi-step, variable workflows (prompting, retrieval, chaining steps); you must manage and track the relationship between input and output because the process and results are dynamic.
- **Expected Output:** ML systems are generally deterministic: the same input row gives the same output every time, with fixed compute/cost for that input size.  

LLM apps are probabilistic and dynamic: the same input can produce different outputs, and both cost and compute vary because input length, output length, and retrieved context all change.  

Also, ML prediction usually has a simple input-to-output flow, while LLM apps often require tracking the full journey from input through retrieval, prompting, and output.

</details>

- **Input:** How can a generator hallucinate despite correct retrieval, and what causes it?
- **Actual Output:** A generator can still “hallucinate” even when retrieval seems correct because errors can come from how the retrieved context is used or from other parts of the pipeline. From your description, the main causes are:

- Wrong documents given or wrong priority ordering: the generator was told to trust higher‑priority documents, but those documents themselves were wrong or were supplied incorrectly. The generator dutifully used them and produced a wrong fact (not a made‑up fact).
- Mixing/confusing sources: the model can combine bits from multiple retrieved items (or the wrong time window, e.g., “six weeks of data”) and produce a mismatched answer.
- Pipeline interaction failures: retriever and generator may individually be OK, but their interaction (how context is assembled, trimmed, or prioritized) can break and produce incorrect outputs.
- Determinism / variability: same input can lead to slightly different outputs each run, so sometimes the generator will return the correct name and other times a wrong one.
- Synthesis errors vs. hallucination boundary: the generator may be correctly following instructions (e.g., synthesize across documents) but the synthesis yields a factually incorrect result (example: asked for student with run no. 123 and it returns “Amit” instead of “Rahul”).

Because of these, you need evaluations at multiple levels (retrieval, generation, and workflow-level) to spot whether the problem is bad documents, bad assembly/prioritization, or true model invention.
- **Expected Output:** A generator can hallucinate even when retrieval is correct by ignoring the retrieved context and producing an answer from its own assumptions or from unrelated parts of the context. This happens because the retriever may fetch the right documents, but the generator can still misread them, over-prioritize certain text, or add unsupported facts.

- **Actual Output:** - Fixed vs. flexible output:
  - Software tests have fixed, deterministic outputs: given the same input the program must produce the same correct answer (pass/fail).
  - LLMs have flexible, probabilistic outputs: the same input can produce different answers and many of those can be acceptable.

- Multi-metric quality vs. single correctness:
  - Traditional software testing mostly checks one thing: correctness (is 2+2 = 4 or not).
  - LLM evaluation is multi-dimensional. You must check correctness, relevance (did it answer the asked question or something else), completeness, grounding (is the answer based on retrieved documents), safety, latency, token/cost, and whether the model is suitable for the target task or production.
