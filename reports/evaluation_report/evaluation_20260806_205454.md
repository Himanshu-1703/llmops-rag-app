## ✅ PASS - test_case_1

<details><summary><b>View Test Case Data</b></summary>

- **Input:** How do ML systems and LLM apps differ in determinism, dynamic cost, and input-output tracking?
- **Actual Output:** - Determinism:
  - Traditional ML: outputs are deterministic. Same input -> same exact output (e.g., 2+3 always = 5). Evaluation can use simple math/formulas and pass/fail tests.
  - LLM apps: outputs are probabilistic and non-deterministic. The same input can produce different, yet valid, answers (different wording, length, or structure). There is no single correct string, so simple assertion-based testing breaks and you need judgement about whether an output is "good."

- Dynamic cost:
  - Traditional ML: cost per workload is roughly fixed and predictable. Example: 100 rows processed = fixed cost (e.g., 10 rupees).
  - LLM apps: cost is dynamic because both input length and output length matter. You pay for input tokens and output tokens, so cost varies and is hard to fix or predict.

- Input–output tracking and evaluation:
  - Traditional ML: relationship between input and output is fixed and easy to track; evaluation is cheap and automated.
  - LLM apps: the relationship is dynamic and semantic (outputs are flexible rather than exact strings). You must manage changing behavior over time, handle failures across multiple components (e.g., retriever vs generator), and perform costly text-based evaluation that often needs human judgment (which does not scale), forcing more complex automated approaches.
- **Expected Output:** ML systems are generally deterministic: the same input row gives the same output every time, with fixed compute/cost for that input size.  

LLM apps are probabilistic and dynamic: the same input can produce different outputs, and both cost and compute vary because input length, output length, and retrieved context all change.  

Also, ML prediction usually has a simple input-to-output flow, while LLM apps often require tracking the full journey from input through retrieval, prompting, and output.

</details>

- **Actual Output:** Even when the retriever returns the right documents, the generator can still hallucinate because it may ignore, mis-use, or misinterpret that context. Concretely:

- The generator can ignore or not properly ground on the provided context and instead invent facts or pull in unrelated content.  
- The LLM itself can have an inherent tendency to produce unsupported outputs (hallucination).  
- A mismatch between your expected output format and the model’s behavior can make the generator produce the “wrong” kind of answer.  
- Prompting injection (malicious or bad content in prompt/context) can override instructions or jailbreak guardrails, causing incorrect outputs.  
- In agentic/autonomous setups, hallucinations can be “silent” (hidden) and harder to detect.

These are the main causes; that’s why you need a generator evaluation pipeline to check that, given a correct query and correct retrieved context, the model actually produces accurate, properly formatted answers.
- **Expected Output:** A generator can hallucinate even when retrieval is correct by ignoring the retrieved context and producing an answer from its own assumptions or from unrelated parts of the context. This happens because the retriever may fetch the right documents, but the generator can still misread them, over-prioritize certain text, or add unsupported facts.

  - Traditional software: outputs are deterministic and fixed. Given the same input (e.g., 2 + 3) you always get the same correct output (5). Tests are simple yes/no pass-fail.

- Multi-metric quality
  - Traditional software: you mostly measure correctness (did it produce the expected value).
  - LLM applications: you must measure multiple dimensions, e.g. correctness, relevance, completeness, groundedness (is the answer based on the source data in a RAG system), and other qualities. An answer can be correct but irrelevant (e.g., gave definition of underfitting when asked about overfitting), or incomplete, or hallucinated.
  - LLM systems often have multiple components (retriever, generator) that can each fail in different ways, so evaluation must diagnose across components.

Crux: software testing checks deterministic logic against a single expected result; LLM evaluation checks whether probabilistic outputs meet a definition of “good” across several metrics, which requires judgment and is not a simple pass/fail.
- **Expected Output:** LLM evals are harder than software tests because:

- **Software tests** usually check **fixed, deterministic output** — one input should produce one expected answer, so it’s mostly **pass/fail**.

Also, software testing mostly checks **correctness only**, while LLM evals need **multi-metric quality checks** like:
- correctness
- relevance
- completeness
- groundedness
- safety

So, unlike software tests, LLM evals are not just about “right or wrong”; they evaluate whether the answer is good across multiple dimensions.
