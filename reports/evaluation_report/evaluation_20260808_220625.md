- **Actual Output:** Note: these two labels (model eval, application/app eval) are informal terms used here to simplify the idea of LLM evals.

Scope
- Model evals: focus on the LLM itself — testing the model’s behavior, capabilities, and outputs.
- App (application) evals: focus on LLM-powered applications or systems — the end-to-end system that uses the LLM in a particular task or product.

Goals
- Model evals: judge the model’s performance and capabilities for given tasks (i.e., how the LLM behaves on benchmarks or task-specific prompts).
- App evals: answer practical product questions — can this system be used for a particular task, is it good enough to ship, can we put it into production given real-world criteria.

Metrics / What “evaluation” means
- LLM evals are not just metrics. They mean the entire testing setup: what you test, the basis/criteria, when you test, and the tools you use. They are systematic and repeatable tests.
- Traditional ML metrics (accuracy, precision, recall, etc.) are examples of metrics you might use, but LLM evals go beyond a single score and include end-to-end testing, criteria for deployability, and practical checks relevant to an application.

Summary
- Both are types of LLM evals (systematic, repeatable tests). Model evals target the model; app evals target the full application and its readiness for real use and shipping. Metrics are part of the picture but not the whole evaluation.
- **Expected Output:** **Model evals vs. app evals in LLM testing**

- **Scope**
  - **Model evals:** Evaluate the **LLM itself**.
  - **App evals:** Evaluate the **LLM-powered application** as a whole or its **components** like retriever, embedding model, or reranker.

- **Goal**
  - **Model evals:** Check the model’s **capabilities, accuracy, and benchmark performance** when a new LLM is released.
  - **App evals:** Check whether the **product works properly** for the intended use case.

- **Metrics**
  - **Model evals:** Benchmarks, leaderboards, accuracy, and capability tests.
  - **App evals:** Correctness of answer, faithfulness, hallucination, relevance, beginner-friendliness, latency, token cost, and component performance.

In short: **model evals test the model; app evals test the product built with the model.**

<details><summary><b>View Test Case Data</b></summary>

- **Input:** How do ML systems and LLM apps differ in determinism, dynamic cost, and input-output tracking?
- **Actual Output:** - Determinism
  - Traditional ML: outputs are deterministic — same input gives the same fixed output.
  - LLM apps: outputs are probabilistic and non-deterministic — the same query can produce very different, yet valid, answers (different wording, length, structure).

- Dynamic cost (evaluation effort)
  - Traditional ML: evaluation is cheap and automated, done by mathematical formulas and clear pass/fail tests.
  - LLM apps: evaluation needs human judgment and detailed textual reports; it is costly because outputs are semantically flexible and there is no single correct answer.

- Input–output tracking (workflow)
  - Traditional ML: prediction is usually a single-step process — you don’t track a long input-to-output journey for each prediction.
  - LLM apps: there is a workflow with multiple components (e.g., retriever, generator); the workflow’s length and complexity vary, components can fail independently, and LLM‑ops must track the whole journey.
- **Expected Output:** ML systems are generally deterministic: the same input row gives the same output every time, with fixed compute/cost for that input size.  

LLM apps are probabilistic and dynamic: the same input can produce different outputs, and both cost and compute vary because input length, output length, and retrieved context all change.  

Also, ML prediction usually has a simple input-to-output flow, while LLM apps often require tracking the full journey from input through retrieval, prompting, and output.

</details>
