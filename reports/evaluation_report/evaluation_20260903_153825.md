<details><summary><b>View Test Case Data</b></summary>

- **Input:** How do ML systems and LLM apps differ in determinism, dynamic cost, and input-output tracking?
- **Actual Output:** - Determinism
  - ML systems (classic regression/classical software): deterministic. Same input gives the same output every time (e.g., a regression model always returns 10 for that input; a calculator always returns 4 for 2+2).
  - LLM apps: probabilistic/dynamic. The same input can produce different outputs on different runs (e.g., you might get 10.5, 11, or 9.5 for the same prompt).

- Dynamic cost / compute
  - ML systems: compute/cost per prediction is stable and predictable. Example: sending 100 rows to a hosted model consumes x units of compute (or 10 rupees in the example) and you'd spend similar x units each time you send 100 rows.
  - LLM apps: compute and cost vary with the input, the output, and retrieved context. Usage is dynamic and changes with the workflow and content.

- Input–output tracking / workflow
  - ML systems (prediction phase): usually no multi-step workflow to track; input → immediate output, so you generally do not track an extended journey from input to output.
  - LLM apps: there is a workflow that can have many steps and varying complexity (prompting, retrieval, chaining, etc.). Because outputs are dynamic, you must manage and track the relationship between input and output across that workflow.
- **Expected Output:** ML systems are generally deterministic: the same input row gives the same output every time, with fixed compute/cost for that input size.  

LLM apps are probabilistic and dynamic: the same input can produce different outputs, and both cost and compute vary because input length, output length, and retrieved context all change.  

Also, ML prediction usually has a simple input-to-output flow, while LLM apps often require tracking the full journey from input through retrieval, prompting, and output.

</details>

## ✅ PASS - test_case_2

<details><summary><b>View Test Case Data</b></summary>

- **Input:** How can a generator hallucinate despite correct retrieval, and what causes it?
- **Actual Output:** A generator can appear to “hallucinate” even when retriever and generator individually test fine because the pipeline and inputs they see in production can still be wrong. Causes from the context:

- Wrong source documents given upstream: the generator was following higher-priority documents that were themselves wrong (e.g., it got “six weeks” from above). It didn’t invent facts; it used bad input.
- Mixing or stitching of retrieved docs: the generator can combine bits from multiple retrieved docs incorrectly, producing a coherent but factually wrong answer (e.g., returning “Amit” instead of “Rahul”).
- Top‑K / retrieval selection issues: if K is limited or the correct doc isn’t in the top K, the generator will only see wrong or less relevant docs and produce wrong output.
- Ordering/prioritization of documents: which documents are presented (and their priority) affects what the generator uses; wrong ordering can lead to wrong answers.
- Determinism / run variability: same input can produce slightly different outputs across runs, so sometimes the generator will return a wrong variant even if components passed tests.

Because these failures arise from interactions and data fed into the generator, component-level evals alone don’t guarantee the end-to-end application will be correct.
- **Expected Output:** A generator can hallucinate even when retrieval is correct by ignoring the retrieved context and producing an answer from its own assumptions or from unrelated parts of the context. This happens because the retriever may fetch the right documents, but the generator can still misread them, over-prioritize certain text, or add unsupported facts.

</details>
