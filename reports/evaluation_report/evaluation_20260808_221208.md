<details><summary><b>View Test Case Data</b></summary>

- **Input:** How do ML systems and LLM apps differ in determinism, dynamic cost, and input-output tracking?
- **Actual Output:** - Determinism
  - Traditional ML: deterministic — same input gives the same output every time (example: a regression model that always returns 10 for a given input).
  - LLM apps: probabilistic and non-deterministic — the same prompt can produce very different outputs (different words, lengths, paragraphing). There is no single fixed correct answer; outputs are semantically flexible.

- Dynamic cost
  - Traditional ML: evaluation is cheap and automated using mathematical formulas.
  - LLM apps: evaluation is costly because you need human judgment and detailed text reports to judge outputs. Also serving and evaluating many text queries implies variable compute/cost (e.g., hosting data and queries on a server incurs compute cost).

- Input–output tracking
  - Traditional ML: easy to track because outputs are fixed for inputs.
  - LLM apps: harder to track — you must manage a moving relationship between input and output, handle semantically flexible (non-exact) outputs, and diagnose failures across multiple components (for example, retriever and generator can fail independently). This makes logging, attribution, and evaluation more complex.
- **Expected Output:** ML systems are generally deterministic: the same input row gives the same output every time, with fixed compute/cost for that input size.  

LLM apps are probabilistic and dynamic: the same input can produce different outputs, and both cost and compute vary because input length, output length, and retrieved context all change.  

Also, ML prediction usually has a simple input-to-output flow, while LLM apps often require tracking the full journey from input through retrieval, prompting, and output.

</details>

## ✅ PASS - test_case_2

<details><summary><b>View Test Case Data</b></summary>

- **Input:** How can a generator hallucinate despite correct retrieval, and what causes it?
- **Actual Output:** Even with correct retrieval, the generator can produce wrong answers because it misuses the retrieved information rather than inventing facts. Causes from the context:

- Wrong document priority/order: the generator was told to rely on “higher priority” docs. If the wrong documents are ranked or flagged as higher priority, the generator will base the answer on those incorrect facts (example: took “Python = 6 weeks” and applied it to “ML = 6 weeks”).
- Mixing facts across documents: the generator can combine pieces from different retrieved docs incorrectly, producing an invalid conclusion.
- Incorrect context composition downstream: individual chunks may be correct, but the set or ordering passed to the generator can be wrong or misleading.
- Instruction/expectation mismatch: if you expect a specific format or precise output but the generator follows different instructions or priorities, the result looks like a hallucination or incorrect output.
- Generator following instructions properly: sometimes it’s not hallucination at all — the generator did what it was told (used the given/high-priority docs), so the error lies in the retrieved/selected documents or their priority, not the generation process.

In short: check document selection/priorities and the instructions you give the generator; the generator often “hallucinates” because of wrong context/prioritization or bad mixing of retrieved facts, not because it made facts up from nowhere.
- **Expected Output:** A generator can hallucinate even when retrieval is correct by ignoring the retrieved context and producing an answer from its own assumptions or from unrelated parts of the context. This happens because the retriever may fetch the right documents, but the generator can still misread them, over-prioritize certain text, or add unsupported facts.
