<details><summary><b>View Test Case Data</b></summary>

- **Input:** How do ML systems and LLM apps differ in determinism, dynamic cost, and input-output tracking?
- **Actual Output:** Determinism
- ML systems: deterministic. Same input => same output (easy pass/fail tests). Example: a calculator giving 2+3=5.
- LLM apps: probabilistic and non-deterministic. Same input can produce different, but valid, answers; outputs are semantically flexible (not exact strings), so exact-match tests fail.

Dynamic cost
- ML systems: cost is predictable and can be fixed per workload. Example: 100 rows of data → cost = 10 rupees.
- LLM apps: cost is dynamic because both input length and output length vary. You pay for input and output tokens, so total cost cannot be fixed easily.

Input–output tracking
- ML systems: input→output relationship is stable and easy to evaluate automatically with simple formulas and assertions.
- LLM apps: the relationship is dynamic and must be actively managed. Outputs can vary in form and content, multiple components (e.g., retriever and generator) can fail independently, and evaluation requires judgment (detailed, often costly text review). Simple assertion-based testing is usually impossible; human annotation doesn’t scale, forcing difficult automated approaches.

Crux: traditional ML tests deterministic correctness; LLM testing must judge whether probabilistic behavior meets a definition of “good.”
- **Expected Output:** ML systems are generally deterministic: the same input row gives the same output every time, with fixed compute/cost for that input size.  

LLM apps are probabilistic and dynamic: the same input can produce different outputs, and both cost and compute vary because input length, output length, and retrieved context all change.  

Also, ML prediction usually has a simple input-to-output flow, while LLM apps often require tracking the full journey from input through retrieval, prompting, and output.

</details>

Multi‑metric quality
- Traditional tests mostly measure a single correctness metric (did it produce the expected value?).
- LLM evaluation must be multi-dimensional: you check correctness, relevance (did it answer the asked question, not a different one), completeness, groundedness (is the answer supported by your data in RAG systems?), etc.
- Multiple system components (e.g., retriever vs. generator) can fail independently, so you need targeted checks across dimensions.
- Because outputs are text and judgments are often subjective, human annotation is costly and doesn’t scale, pushing the need for careful automated evaluation strategies.

Also, software testing mostly checks **correctness only**, while LLM evals need **multi-metric quality checks** like:
- correctness
- relevance
- completeness
- groundedness
- safety

So, unlike software tests, LLM evals are not just about “right or wrong”; they evaluate whether the answer is good across multiple dimensions.
