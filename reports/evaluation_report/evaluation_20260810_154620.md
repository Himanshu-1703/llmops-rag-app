- **Input:** How do ML systems and LLM apps differ in determinism, dynamic cost, and input-output tracking?
- **Actual Output:** - Determinism
  - ML systems: deterministic. Same input → same output every time (example: regression gives 10 for that input; calculator 2+2=4).
  - LLM apps: probabilistic/non-deterministic. The same input can produce different outputs on different runs (semantic text can vary even if meaning is similar).

- Dynamic cost
  - ML systems: costs and compute are more predictable and tied to the model/dataset you host (e.g., 100 rows on an AWS server incur predictable compute/cost).
  - LLM apps: costs are more dynamic because multiple moving components (retriever, generator/LLM, etc.) and the need for repeated generation, retrieval, and human-quality checks increase compute and evaluation cost.

- Input–output tracking and evaluation
  - ML systems: easier to track and evaluate. Fixed labels or numeric outputs let you compare with simple mathematical metrics; only the model is the main thing to evaluate.
  - LLM apps: harder to track and evaluate. Outputs vary in wording; you must judge semantic equivalence rather than exact matches. Multiple components produce the final output, so you must manage the relationship between inputs and outputs and often rely on human judgment and detailed (costly) reports.
- **Expected Output:** ML systems are generally deterministic: the same input row gives the same output every time, with fixed compute/cost for that input size.  

LLM apps are probabilistic and dynamic: the same input can produce different outputs, and both cost and compute vary because input length, output length, and retrieved context all change.  

Also, ML prediction usually has a simple input-to-output flow, while LLM apps often require tracking the full journey from input through retrieval, prompting, and output.

</details>

## ❌ FAIL - test_case_2

<details><summary><b>View Test Case Data</b></summary>

- **Input:** How can a generator hallucinate despite correct retrieval, and what causes it?
- **Actual Output:** - Wrong or mis-prioritized documents: the generator may be told to rely on “higher priority” documents. If those documents are wrong or the retriever returned the wrong ones (or ordered them badly), the generator will produce answers based on that bad input — not a free-floating hallucination but a faithful use of wrong context.

- Mixing / splicing across documents: the generator can combine pieces from multiple retrieved docs into a single, incorrect fact (it “mixes up” data), producing a plausible but wrong answer.

- Instruction-following vs. hallucination: the model may be strictly following your instructions (e.g., use top documents) and thus produce incorrect output because the input it used was wrong, not because it invented facts out of thin air.

- Non‑determinism: same query + context can give slightly different outputs each run, so one run may be correct and another incorrect.

- Format / expectation mismatch: the generator might produce an answer in a different form than you expect (causing your app to treat it as wrong), or produce the right kind of reply but with incorrect factual content (e.g., returns “Amit” instead of the true “Rahul”).

Takeaway: evaluate both retriever and generator separately — bad retrieval or document ordering and generator mixing/variation are common causes of “hallucination” in a RAG pipeline.
- **Expected Output:** A generator can hallucinate even when retrieval is correct by ignoring the retrieved context and producing an answer from its own assumptions or from unrelated parts of the context. This happens because the retriever may fetch the right documents, but the generator can still misread them, over-prioritize certain text, or add unsupported facts.

</details>

  - App/chat process emits events to an in-memory buffer or local fast writer.
  - Push events to an async message bus / queue (event stream) immediately (fire-and-forget from the request path).
  - Separate ingestion workers consume the stream and persist into the durable store (data warehouse / observability tool like Langsmith).
- Backpressure / failure: if the queue is full, fall back to a local retry buffer and retry ingestion; do not block serving.
- Acknowledge the chat request independently of successful persistence.

2) Core schema (append-only, queryable)
- messages (one row per turn)
  - message_id (UUID)
  - conversation_id / session_id (UUID) — primary linkage for late-signal attachment
  - user_id (pseudonymized or hashed id)
  - turn_index (integer) — incremental per conversation
  - timestamp (ISO)
  - role (user / assistant / system)
  - text_masked (masked/redacted text for PII) — safe to query
  - text_ref (nullable) — pointer/token to encrypted raw text in PII vault (see PII section)
  - response_text_masked
  - model_version / model_meta
  - latency_ms (server-side)
  - captured_signals (JSON) — e.g., {"thumbs_up": true}
  - metadata (JSON) — client, channel, locale, tags
  - ingestion_status (enum) — persisted / pending / failed

- events / signals (append-only, tracks early and late signals)
  - signal_id (UUID)
  - conversation_id (UUID)
  - message_id (nullable) — can attach to a specific turn or null for session-level
  - signal_type (enum) — thumbs_up, escalation_email, support_ticket, rating, etc.
  - signal_value (string / JSON)
  - source (string) — chat-ui, email, support-system
  - timestamp_received
  - attached_at (timestamp when ingested)
  - provenance_metadata (JSON)

- computed_signals (store offline or nearline computed metrics)
  - computed_id (UUID)
  - conversation_id
  - metric_name (e.g., "helpfulness_score", "avg_response_time")
  - metric_value (float / JSON)
  - compute_time

3) Indexing & query patterns
- Index conversation_id, user_id (hashed), timestamp, turn_index, and signal_type for fast retrieval.
- Partition messages by date and/or conversation shard for large scale.
- Use JSON columns for flexible captured_signals and metadata to enable filtering.

4) Late-signal attachment
- Always include conversation_id in every external signal (email ticket, follow-up survey).
- Ingest late signals into the events/signals table and link by conversation_id (and message_id when known).
- Use an append-only approach; do not overwrite original messages. If needed, create a derived materialized view that joins messages + signals to produce a timeline.

- Detect PII at ingestion time (basic detectors in the ingestion worker).

    - message_id
    - pii_type (phone, email, card, address)
