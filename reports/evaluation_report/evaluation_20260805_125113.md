<details><summary><b>View Test Case Data</b></summary>

- **Input:** How do ML systems and LLM apps differ in determinism, dynamic cost, and input-output tracking?
- **Actual Output:** - Determinism
  - Traditional ML: outputs are deterministic — same input gives the same, exact output (e.g., a calculator always returns 5 for 2+3). Tests are simple pass/fail.
  - LLM apps: outputs are probabilistic and non-deterministic — the same input can produce different, yet valid, outputs. There is no single correct string, so simple assertion tests break down.

- Dynamic cost
  - Traditional ML: cost is predictable and tied to fixed data/computation (e.g., 100 rows → fixed compute/cost).
  - LLM apps: cost is dynamic and hard to fix because both input length and output length vary. You pay for input tokens and output tokens, so total cost changes per request.

- Input–output tracking and evaluation
  - Traditional ML: the relationship between input and output is stable and easy to manage; evaluation can be cheap and automated using formulas.
  - LLM apps: the relationship is moving and requires judgment. Outputs are semantically flexible (not exact strings), evaluation is costly (often needs detailed human-quality reports), human annotation doesn’t scale, and multiple components (e.g., retriever vs generator) can fail independently, making tracking and automated testing difficult.
- **Expected Output:** ML systems are generally deterministic: the same input row gives the same output every time, with fixed compute/cost for that input size.  

LLM apps are probabilistic and dynamic: the same input can produce different outputs, and both cost and compute vary because input length, output length, and retrieved context all change.  

Also, ML prediction usually has a simple input-to-output flow, while LLM apps often require tracking the full journey from input through retrieval, prompting, and output.

</details>

<details><summary><b>View Test Case Data</b></summary>

- **Input:** How do LLM evals differ from software tests in fixed vs. flexible output and multi-metric quality?
- **Actual Output:** Fixed vs. flexible output
- Traditional software: deterministic — one fixed correct output for a given input (e.g., calculator: 2 + 3 = 5). Tests are exact string/value checks.
- LLMs: probabilistic and semantically flexible — the same input can produce many different, equally valid outputs (different words, lengths, styles). Exact assertion-based tests often fail because correct answers are not a single fixed string.

Multi-metric quality
- Traditional software: mainly a single correctness check (pass/fail).
- LLM-based apps: require multi-dimensional evaluation — correctness, relevance, completeness, groundedness (is the answer based on the source data in RAG systems), etc.
- Example from context: an LLM that gives the definition of underfitting when asked about overfitting is “correct” textually but not relevant.
- Additional complexity: LLM apps often combine components (retriever, generator) that can fail in different ways, so you must evaluate each dimension/component, not just a single boolean.

Practical consequences (from context)
- Non-determinism and semantic flexibility create a grey area; human annotation is costly and doesn’t scale, pushing toward automated but more complex evaluation methods.
- **Expected Output:** LLM evals are harder than software tests because:

- **Software tests** usually check **fixed, deterministic output** — one input should produce one expected answer, so it’s mostly **pass/fail**.
- **LLM evals** deal with **flexible, probabilistic output** — the same prompt can produce different but still valid answers.

Also, software testing mostly checks **correctness only**, while LLM evals need **multi-metric quality checks** like:
- correctness
- relevance
- completeness
- groundedness
