<details><summary><b>View Test Case Data</b></summary>

- **Input:** How do ML systems and LLM apps differ in determinism, dynamic cost, and input-output tracking?
- **Actual Output:** Determinism
- Traditional ML: largely deterministic. Given the same input (e.g., a regression feature row) you get the same numeric label every time.
- LLM apps: probabilistic and non‑deterministic. The same prompt can produce different but valid outputs on different runs.

Dynamic cost
- Traditional ML: evaluation is cheap and mostly automated (mathematical metrics on fixed labels).
- LLM apps: evaluation is costly because outputs are free‑form text and need human judgment or expensive annotation; automated checks are harder to trust.

Input–output tracking
- Traditional ML: fixed labels and one moving component (the model) make it easy to match inputs to outputs and measure correctness.
- LLM apps: outputs are semantically flexible (different strings can be correct), and systems often have multiple independent components (retriever, generator, etc.) that can fail in different ways. That makes tracing which input caused which output and why much harder.
- **Expected Output:** ML systems are generally deterministic: the same input row gives the same output every time, with fixed compute/cost for that input size.  

LLM apps are probabilistic and dynamic: the same input can produce different outputs, and both cost and compute vary because input length, output length, and retrieved context all change.  

Also, ML prediction usually has a simple input-to-output flow, while LLM apps often require tracking the full journey from input through retrieval, prompting, and output.

</details>

- **Input:** How do LLM evals differ from software tests in fixed vs. flexible output and multi-metric quality?
- **Actual Output:** Fixed vs. flexible output
- Traditional software tests expect deterministic, exact outputs (e.g., 2+3 must be 5). Simple assertion checks work.
- LLM outputs are semantically flexible: many different strings can be correct for the same input. Exact-string checks will wrongly reject valid answers.
- Therefore LLM evals must judge semantic equivalence or accept multiple valid outputs, not just exact matches.

Multi-metric quality
- Traditional tests are often binary (pass/fail) against a single expected result.
- LLM-based systems are probabilistic and multi-faceted: different quality aspects matter (and different components like retriever and generator can fail independently).
- So evaluation needs multiple metrics to capture those different aspects (e.g., semantic correctness, relevance, fluency, safety/factuality) rather than a single yes/no.
- Because outputs vary and evaluation of text is costly, LLM evals must be systematic, repeatable, and based on clear criteria, often aggregating results across runs instead of single assertions.
- **Expected Output:** LLM evals are harder than software tests because:

- **Software tests** usually check **fixed, deterministic output** — one input should produce one expected answer, so it’s mostly **pass/fail**.
- **LLM evals** deal with **flexible, probabilistic output** — the same prompt can produce different but still valid answers.

Also, software testing mostly checks **correctness only**, while LLM evals need **multi-metric quality checks** like:
- correctness
- relevance
- completeness
- groundedness
- safety

So, unlike software tests, LLM evals are not just about “right or wrong”; they evaluate whether the answer is good across multiple dimensions.

How to make it non‑blocking
- Fire‑and‑forget async pipeline:
  - Client/chat server writes log event to a local buffer or an in‑memory queue. Return response to user immediately.
  - A background worker reads the buffer and pushes events to a durable message queue (Kafka, PubSub, SQS).
  - Downstream consumers persist to the data warehouse/observability tool.
- Backpressure and graceful degradation:
  - If queue is full, sample or persist logs to local disk and retry; raise alerts rather than blocking user traffic.
- Batching & compression in the worker to reduce write overhead and cost.

Durable, queryable storage
- Use message queue → ETL → data warehouse or observability store (Langsmith) as final sink.
- Keep events append‑only; use event timestamps + ingestion timestamps.
- Encrypt in transit and at rest; enforce RBAC and audit logging on the warehouse.

Identifiers and IDs (consistent, deterministic)
