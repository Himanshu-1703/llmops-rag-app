<details><summary><b>View Test Case Data</b></summary>

- **Input:** How do ML systems and LLM apps differ in determinism, dynamic cost, and input-output tracking?
- **Actual Output:** - Determinism
  - ML systems: deterministic — same input gives the same output every time (e.g., a calculator: 2 + 3 = 5). Tests are pass/fail.
  - LLM apps: probabilistic/non‑deterministic — the same input can produce different, semantically acceptable outputs. There is no single exact correct string, so testing needs judgment against a definition of “good” rather than strict equality.

- Dynamic cost
  - ML systems: cost is predictable and can be fixed per dataset or call (example in context: 100 rows → cost 10 rupees).
  - LLM apps: cost is variable because both input length and output length matter. You pay for input and output tokens, so total cost can’t be fixed and is harder to predict. Evaluation is also more expensive because text outputs need detailed (often human) review.

- Input–output tracking / monitoring
  - ML systems: static, fixed mapping between input and output, easy to track and evaluate with automated formulas.
  - LLM apps: relationship is dynamic — outputs move and vary, so you must actively manage and monitor the input→output relationship. Outputs are semantically flexible, different components (e.g., retriever vs. generator) can fail independently, and simple assertion tests become ineffective. Human annotation doesn’t scale, so new automated evaluation and monitoring approaches are needed.
- **Expected Output:** ML systems are generally deterministic: the same input row gives the same output every time, with fixed compute/cost for that input size.  

LLM apps are probabilistic and dynamic: the same input can produce different outputs, and both cost and compute vary because input length, output length, and retrieved context all change.  

Also, ML prediction usually has a simple input-to-output flow, while LLM apps often require tracking the full journey from input through retrieval, prompting, and output.

</details>

- **Input:** How do LLM evals differ from software tests in fixed vs. flexible output and multi-metric quality?
- **Actual Output:** - Fixed vs. flexible output
  - Traditional software: outputs are deterministic and fixed. Given the same input (2 and 3) the output can only be one value (5). Tests are simple assertions: pass or fail.
  - LLMs: outputs are probabilistic and flexible. The same prompt can yield many different but valid answers (different words, length, style). Outputs are semantically flexible (not exact strings), so two different texts can both be correct.

- Multi-metric quality vs. single correctness
  - Traditional software: you usually measure only correctness (did it produce the expected value?).
  - LLM applications: evaluation is multi-dimensional. You must check correctness, relevance, completeness, grounding (is the answer based on the source or hallucinated?), and more. Components (e.g., retriever and generator) can fail independently, so you often need component-level evaluation too.

Additional consequences (from the same points)
  - Simple assertion-based tests often fail for LLMs because outputs vary.
  - Evaluation is costlier and often requires human judgment and detailed reports; human annotation does not scale, pushing toward automated but harder-to-design metrics.
- **Expected Output:** LLM evals are harder than software tests because:

- **Software tests** usually check **fixed, deterministic output** — one input should produce one expected answer, so it’s mostly **pass/fail**.
- **LLM evals** deal with **flexible, probabilistic output** — the same prompt can produce different but still valid answers.

Also, software testing mostly checks **correctness only**, while LLM evals need **multi-metric quality checks** like:
- correctness
- relevance
- completeness
- groundedness
- safety

So, unlike software tests, LLM evals are not just about “right or wrong”; they evaluate whether the answer is good across multiple dimensions.
