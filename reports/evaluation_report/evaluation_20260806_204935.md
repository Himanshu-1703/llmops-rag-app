## ✅ PASS - test_case_1

<details><summary><b>View Test Case Data</b></summary>

- **Input:** How do ML systems and LLM apps differ in determinism, dynamic cost, and input-output tracking?
- **Actual Output:** Determinism
- Traditional ML: outputs are deterministic. Same input → same, exact output (like a calculator: 2+3 always = 5). Tests are simple pass/fail using exact assertions.
- LLM apps: outputs are probabilistic and non‑deterministic. The same input can produce different, but valid, answers (different wording, length, structure). There is no single “correct” string, so simple assertion tests often fail.

Dynamic cost
- Traditional ML: cost is predictable and fixed per workload. Example from context: 100 rows → fixed compute cost (say 10 rupees).
- LLM apps: cost is dynamic and hard to fix because both input length and output length matter. You pay for tokens in and tokens out, so cost varies per request and is difficult to judge ahead of time.

Input–output tracking / evaluation
- Traditional ML: relationship between input and output is stable and easy to track; evaluation can be cheap and automated (mathematical formulas).
- LLM apps: relationship is dynamic and semantically flexible. Outputs aren’t exact strings, so you need human judgement or complex evaluation methods. Human annotation is costly and doesn’t scale; multiple components (e.g., retriever and generator) can fail independently, making diagnosis harder. Overall, you must manage a moving, probabilistic input→output relationship rather than a fixed mapping.
- **Expected Output:** ML systems are generally deterministic: the same input row gives the same output every time, with fixed compute/cost for that input size.  

LLM apps are probabilistic and dynamic: the same input can produce different outputs, and both cost and compute vary because input length, output length, and retrieved context all change.  

Also, ML prediction usually has a simple input-to-output flow, while LLM apps often require tracking the full journey from input through retrieval, prompting, and output.

</details>

## ✅ PASS - test_case_12

<details><summary><b>View Test Case Data</b></summary>

- **Input:** How do LLM evals differ from software tests in fixed vs. flexible output and multi-metric quality?
- **Actual Output:** Fixed vs. flexible output
- Traditional software is deterministic: the same input gives one fixed correct output (e.g., 2 + 3 must be 5). Tests can assert exact equality.
- LLMs are probabilistic and semantically flexible: the same prompt can produce many different, equally valid answers (different words, lengths, structure). Exact-string assertions fail here; you must allow for varied but correct outputs.

Multi‑metric quality
- Traditional tests measure a single binary notion: correctness (did it produce the expected value?).
- LLM evaluations are multi‑dimensional. You must judge correctness plus other qualities such as relevance, completeness, and groundedness (e.g., did a RAG system base its answer on the retrieved data or hallucinate?). Different components (retriever vs. generator) can fail in different ways, so you need separate checks and human judgment or costly annotation/automated proxies to assess overall quality.
- **Expected Output:** LLM evals are harder than software tests because:

- **Software tests** usually check **fixed, deterministic output** — one input should produce one expected answer, so it’s mostly **pass/fail**.
- **LLM evals** deal with **flexible, probabilistic output** — the same prompt can produce different but still valid answers.

Also, software testing mostly checks **correctness only**, while LLM evals need **multi-metric quality checks** like:
- correctness
- relevance
- completeness
- groundedness
- safety

So, unlike software tests, LLM evals are not just about “right or wrong”; they evaluate whether the answer is good across multiple dimensions.

</details>
