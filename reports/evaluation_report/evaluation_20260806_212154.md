- **Actual Output:** - Determinism:
  - ML systems: deterministic — same input -> same, exact output (you can write simple pass/fail tests).
  - LLM apps: probabilistic/non‑deterministic — same input can produce different, but valid, outputs; responses are semantically flexible rather than fixed strings.

- Dynamic cost:
  - ML systems: cost is predictable for a given dataset/workload (example: 100 rows -> cost = 10 rupees).
  - LLM apps: cost is dynamic and hard to fix because both input length and output length drive cost; you can’t easily predict total cost beforehand.

- Input–output tracking and evaluation:
  - ML systems: input→output relationship is stable and easy to evaluate with automated mathematical checks.
  - LLM apps: relationship is fluid — you must “manage” a moving relationship between inputs and varied outputs; evaluation is costly (needs detailed judgment/reports, human annotation doesn’t scale), outputs are semantically flexible, and multiple components (e.g., retriever vs generator) can fail independently, so simple assertion‑based testing is insufficient.
- **Expected Output:** ML systems are generally deterministic: the same input row gives the same output every time, with fixed compute/cost for that input size.  

LLM apps are probabilistic and dynamic: the same input can produce different outputs, and both cost and compute vary because input length, output length, and retrieved context all change.  

Also, ML prediction usually has a simple input-to-output flow, while LLM apps often require tracking the full journey from input through retrieval, prompting, and output.

## ✅ PASS - test_case_12

<details><summary><b>View Test Case Data</b></summary>

- **Input:** How do LLM evals differ from software tests in fixed vs. flexible output and multi-metric quality?
- **Actual Output:** Fixed vs. flexible output
- Traditional software: outputs are fixed and deterministic. A given input has a single correct output (e.g., 2+3 → 5). Tests are simple assert/pass/fail based on exact expected value.
- LLMs: outputs are probabilistic and semantically flexible. The same input can produce many different but valid answers (different words, lengths, phrasing). Exact-string checks are often meaningless because multiple different outputs can all be correct.

Multi-metric quality vs. single correctness
- Traditional software: you mainly measure correctness (did it produce the expected value or not).
- LLM applications: you need multi-dimensional evaluation. Besides correctness you must judge relevance, completeness, groundedness (e.g., is the answer based on the provided data in a RAG system), and other qualities. Different components (retriever, generator) can fail independently, so you must evaluate multiple parts and failure modes. Because outputs are text and non-deterministic, evaluation often requires human judgment, is costly, and simple assertion-based testing often won’t work.
- **Expected Output:** LLM evals are harder than software tests because:

- **Software tests** usually check **fixed, deterministic output** — one input should produce one expected answer, so it’s mostly **pass/fail**.
- **LLM evals** deal with **flexible, probabilistic output** — the same prompt can produce different but still valid answers.

Also, software testing mostly checks **correctness only**, while LLM evals need **multi-metric quality checks** like:
- correctness
- relevance
- completeness
- groundedness
- safety

So, unlike software tests, LLM evals are not just about “right or wrong”; they evaluate whether the answer is good across multiple dimensions.

</details>
