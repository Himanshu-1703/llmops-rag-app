<details><summary><b>View Test Case Data</b></summary>

- **Input:** How do ML systems and LLM apps differ in determinism, dynamic cost, and input-output tracking?
- **Actual Output:** - Determinism
  - ML systems: deterministic. For the same input you get the same fixed label or value (e.g., give 100 rows, model always returns the same result). Tests are pass/fail.
  - LLM apps: probabilistic and non‑deterministic. The same input can produce different outputs (different words, lengths, sentences) while still being valid if the semantic meaning matches.

- Dynamic cost
  - ML systems: cost is predictable and tied to compute/data size (example: 100 rows → cost 10 rupees). You can plan and fix costs.
  - LLM apps: costs and compute behavior are dynamic and harder to fix; evaluation and quality checking are also more costly because they need human judgment and detailed reports rather than cheap automated formulas.

- Input–output tracking
  - ML systems: only one main moving part (the model). Inputs map to fixed labels, so tracking and evaluating input→output is straightforward.
  - LLM apps: multiple components (e.g., retriever + LLM generator). Outputs vary semantically, so you must actively manage the relationship between input and output; evaluation requires semantic checks and human judgment, making tracking harder.
- **Expected Output:** ML systems are generally deterministic: the same input row gives the same output every time, with fixed compute/cost for that input size.  

LLM apps are probabilistic and dynamic: the same input can produce different outputs, and both cost and compute vary because input length, output length, and retrieved context all change.  

Also, ML prediction usually has a simple input-to-output flow, while LLM apps often require tracking the full journey from input through retrieval, prompting, and output.

</details>

## ✅ PASS - test_case_2

<details><summary><b>View Test Case Data</b></summary>

- **Input:** How can a generator hallucinate despite correct retrieval, and what causes it?
- **Actual Output:** Even if the retriever returns the “right” documents, the generator can still hallucinate because it must interpret, combine, and present that retrieved context together with the user query and system instructions. Causes (from the given context):

- Bad or low‑quality context: if the data or the way it was put into the vector store is wrong or noisy, the generator will produce wrong facts even while following instructions.  
- Mixing up retrieved items: the generator can merge pieces from multiple retrieved documents and produce a coherent but factually incorrect answer (example: it pulled six weeks of data and mixed things up).  
- Pipeline/workflow interaction problems: retriever and generator may each work fine alone, but their interaction (how context is assembled and fed to the generator) can break the application and create errors.  
- Limited control over the user query: the LLM gets an augmented prompt (user query) that you can’t control, so errors in the context have more impact.  
- Determinism/variability: the same inputs can give slightly different outputs across runs, causing inconsistent or incorrect facts.  
- Model behavior: the generator may be diligently following instructions but still produce a factually incorrect answer (e.g., returning “Amit” instead of “Rahul”) because it misapplied the retrieved context.

Because of these points, you need not only component-level checks but workflow‑level evaluation to flag such errors.
- **Expected Output:** A generator can hallucinate even when retrieval is correct by ignoring the retrieved context and producing an answer from its own assumptions or from unrelated parts of the context. This happens because the retriever may fetch the right documents, but the generator can still misread them, over-prioritize certain text, or add unsupported facts.

</details>

## ✅ PASS - test_case_12

<details><summary><b>View Test Case Data</b></summary>

- **Input:** How do LLM evals differ from software tests in fixed vs. flexible output and multi-metric quality?
- **Actual Output:** - Fixed vs flexible output:
  - Fixed output (software) = deterministic. Same input -> same exact output (e.g., 2+3 must be 5). Tests are binary: pass or fail.
  - Flexible output (LLMs) = probabilistic. Same input can produce very different but still valid outputs (different wording, length, structure). Evaluation must allow for this variability.

- Single-metric vs multi-metric quality:
  - Software tests focus on correctness only: does the program produce the expected result?
  - LLM evals are multi-dimensional: you check correctness, relevance, completeness, groundedness (e.g., is a RAG answer based on retrieved context or hallucinated), and more. An answer can be correct but irrelevant (asked “overfitting” and got definition of “underfitting”).

- Scope of testing:
  - Software testing is usually test cases and pass/fail results.
  - LLM evals are the entire testing setup: what you test, on what basis, when you test, and what tools you use. The goal is practical: can the model be used for a task, is it production-ready, did a prompt change improve results, is RAG grounded—not just a single score.
- **Expected Output:** LLM evals are harder than software tests because:

- **Software tests** usually check **fixed, deterministic output** — one input should produce one expected answer, so it’s mostly **pass/fail**.
- **LLM evals** deal with **flexible, probabilistic output** — the same prompt can produce different but still valid answers.

Also, software testing mostly checks **correctness only**, while LLM evals need **multi-metric quality checks** like:
- correctness
- relevance
- completeness
- groundedness
- safety

So, unlike software tests, LLM evals are not just about “right or wrong”; they evaluate whether the answer is good across multiple dimensions.
