<details><summary><b>View Test Case Data</b></summary>

- **Input:** How do ML systems and LLM apps differ in determinism, dynamic cost, and input-output tracking?
- **Actual Output:** Determinism
- Traditional ML / software: deterministic. Same input → same output every time (calculator or login examples).  
- LLM apps: probabilistic and non‑deterministic. The same input can produce different outputs on different runs (e.g., ChatGPT giving different answers).

Dynamic cost
- Traditional ML: costs are more static and predictable — tied to dataset size, model hosting, and compute (example: hosting a model on AWS for 100 rows incurs a calculable compute cost). Evaluation is cheap and automated (mathematical formulas).  
- LLM apps: costs are more dynamic and typically higher — multiple components (retriever, LLM/generator, etc.) consume compute, and evaluation requires human judgment and detailed reports, which are costly. Because outputs and components move dynamically, costs and resource needs can change.

Input–output tracking
- Traditional ML: easy to track and compare. Labels are fixed (e.g., 0 or 1), only the model is the main moving part, and automated metrics let you match predictions to labels straightforwardly.  
- LLM apps: hard to track and evaluate. Outputs are complex and semantic (different text can have the same meaning), multiple components influence results, and nondeterminism means you must actively manage the relationship between inputs and outputs and often rely on human judgment to evaluate correctness.
- **Expected Output:** ML systems are generally deterministic: the same input row gives the same output every time, with fixed compute/cost for that input size.  

LLM apps are probabilistic and dynamic: the same input can produce different outputs, and both cost and compute vary because input length, output length, and retrieved context all change.  

Also, ML prediction usually has a simple input-to-output flow, while LLM apps often require tracking the full journey from input through retrieval, prompting, and output.

</details>

- **Input:** Recommend non-blocking, durable, queryable logging schema incl. turn/user/session IDs, late-signal attachment, PII handling.
- **Actual Output:** Schema (tables/records you should keep)
- session (one row per conversation)
  - session_id (canonical conversation ID)
  - user_id (nullable; use pseudonymous ID if PII removed)
  - created_at, ended_at
  - channel/source (web, mobile, email, etc.)

  - turn_id (unique per session)
  - session_id
  - turn_index (0,1,2...)
  - role (user / assistant / system)
  - timestamp
  - latency_ms (assistant response time)
  - message_id (if you need message-level ids)

  - signal_id
  - session_id
  - turn_id (nullable)
  - signal_type (thumbs_up, thumbs_down, rating, escalate, email_received, etc.)
  - value (e.g., +1/-1, numeric rating, text)
  - source (in-chat, email, support ticket)
  - timestamp

  - metric_id
  - session_id

  - metric_value
  - aggregation_window (optional)
  - computed_at

- late_signals / external_events
  - late_signal_id
  - session_id (must be present to attach)
  - referenced_turn_id (optional)

  - event_payload (JSON; raw)
  - event_received_at
  - attached_at (when it was linked to session)
  - original_event_id (from external system)

  - pii_token_id (opaque token)
  - session_id
  - turn_id (optional)
  - pii_type (phone, address, card, SSN)
  - encrypted_payload (encrypted raw data; NOT in normal logs)
  - stored_at
  - access_control_metadata (who/why accessed)
  - retention_expiry

Key engineering principles (how to implement)

1) Non-blocking logging (must not increase latency)
- Fire-and-forget from conversational path: do not wait for logging writes. Push log events to an async pipeline (in-memory buffer → durable queue or lightweight async writer).
- Use background workers or streaming ingestion to write into your durable store (data warehouse / observability tool like Langsmith).
- Have bounded buffer + backpressure strategy: if pipeline is overloaded, sample or drop non-critical logs, but always persist critical events (errors, escalations).
- Make logging idempotent (include event_id) so retries do not create duplicates.

2) Durability & queryability
- Write durable, append-only events into a warehouse/observability store (or tools like Langsmith). Keep full event timestamps and canonical IDs.
- Use normalized tables above plus derived denormalized tables for fast queries and dashboards.
- Partition by date and/or session_id, and add indexes on session_id, user_id, turn_id, and event_type for fast retrieval.
- Store metadata as structured JSON when schema-flexibility is needed, but keep main query fields as columns.

3) Late-signal attachment
- Always include session_id (conversation ID) and turn timestamps in every log. Late events must carry the session_id so they can be matched.
- Store late signals as separate rows in late_signals table; do not overwrite original conversation events—append and link by session_id/turn_id.
- Provide a background backfill/attachment process that:
  - Consumes late events (e.g., support emails, tickets).
  - Matches them to sessions using session_id or heuristics (user_id + time window + content hash).
  - Writes link rows (late_signals.attached_at) and updates computed_signals if needed.
- Keep an audit trail of attachments (who/what linked and when).

4) PII handling
- Detect PII at ingress (automated detector or user-declared). Classify types (phone, address, card).
- Do not store raw PII in normal logs. Instead:
  - Redact PII in content_redacted (replace with placeholders).
  - Store raw PII only in pii_store with strong encryption, strict ACLs, logging of access, and limited retention.
  - In primary logs keep a pointer (content_hash or pii_token_id) to the secure PII store so you can rehydrate if authorized.
- Record consent_flags per session and respect them for PII storage and retention.
- Retention & deletion: have automated TTLs for pii_store and the ability to purge all data for a session/user upon request (right to be forgotten).
- Audit access to raw PII (who, why, when) and surface that in observability.

Captured vs computed signals (how to store)
- Captured signals: write immediately as captured_signals rows (thumbs up/down example). These are raw user-supplied signals.
- Computed signals: compute off the event stream in batch or streaming jobs and write into computed_signals. Keep computed jobs idempotent and timestamped.

Operational details
- Use unique IDs everywhere (session_id, turn_id, event_id) and make them searchable.
- Keep timestamps in UTC and include both event_time (when user acted) and ingested_at (when logged).
- Keep an append-only audit log for changes (attachments, deletions).
- Provide APIs to query by session_id or to fetch full session (join session → turns → captured_signals → late_signals) for replay and debugging.
- If using an observability tool like Langsmith, map these tables/fields into the tool’s ingestion schema and keep raw event export to your warehouse for ad-hoc queries.

Example minimal record (turn)
- session_id: s_123
- turn_id: t_0005
- turn_index: 4
- role: user
- timestamp: 2026-08-31T12:00:00Z
- content_redacted: "My phone is [REDACTED]"
- content_hash: sha256(...)
- pii_token_id: p_987 (if phone stored securely)
- latency_ms: 320
- captured_signals: []
- meta: { model: "gpt-x", tokens: 128 }

This schema and architecture satisfy: non-blocking writes (async), durable and queryable storage (warehouse/Langsmith), late-signal attachment (late_signals linked by session_id), and safe PII handling (redaction + encrypted secure store + consent + audit).
