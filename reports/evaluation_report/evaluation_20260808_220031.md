- **Actual Output:** - Determinism
  - Traditional ML: outputs are largely deterministic — the same input gives the same output. That makes testing binary (pass/fail).
  - LLM apps: outputs are probabilistic and non-deterministic — the same input can produce different, yet valid, responses. Outputs are semantically flexible (different words/lengths can all be correct).

- Dynamic cost (evaluation effort)
  - Traditional ML: evaluation is cheap and automated using mathematical formulas and metrics.
  - LLM apps: evaluation needs human judgment and detailed textual reports, so it is more costly and time-consuming.

- Input-output tracking
  - Traditional ML: fixed outputs make tracking and automated test cases straightforward; versioning of model/data pipelines and artifacts supports reproducible evaluation.
  - LLM apps: input→output is harder to track because outputs aren’t exact strings and there’s no single correct answer. Also, multiple components (e.g., retriever vs LLM) are separate and can fail independently, so you need richer tracking, component versioning, and manual or complex evaluation processes.
- **Expected Output:** ML systems are generally deterministic: the same input row gives the same output every time, with fixed compute/cost for that input size.  

LLM apps are probabilistic and dynamic: the same input can produce different outputs, and both cost and compute vary because input length, output length, and retrieved context all change.  

Also, ML prediction usually has a simple input-to-output flow, while LLM apps often require tracking the full journey from input through retrieval, prompting, and output.

- **Actual Output:** - Fixed vs flexible output
  - Software tests expect deterministic, fixed outputs: the same input gives the same correct answer, so test cases pass or fail unambiguously.
  - LLM outputs are probabilistic and flexible: the same input can produce many different valid responses (different words, lengths, styles). That makes strict pass/fail testing inappropriate — you must allow for variability and judge whether the output meets a definition of “good” rather than exactly matching a single expected string.

- Multi-metric quality
  - LLM evals treat quality as multi-dimensional, not a single binary property. You evaluate aspects like correctness, relevance, fluency, tone, completeness, etc., against clear criteria.
  - Because of that, LLM evaluations are designed to be systematic and repeatable and use explicit criteria for each metric so you can judge probabilistic behavior consistently rather than relying on a single test case pass/fail.
- **Expected Output:** LLM evals are harder than software tests because:

- **Software tests** usually check **fixed, deterministic output** — one input should produce one expected answer, so it’s mostly **pass/fail**.
- **LLM evals** deal with **flexible, probabilistic output** — the same prompt can produce different but still valid answers.

Also, software testing mostly checks **correctness only**, while LLM evals need **multi-metric quality checks** like:
- correctness
- relevance
- completeness
- groundedness
- safety

So, unlike software tests, LLM evals are not just about “right or wrong”; they evaluate whether the answer is good across multiple dimensions.

1) High‑level pattern (non‑blocking)
- Keep conversation runtime and logging separate: emit log events synchronously to a local, in‑memory buffer or lightweight queue, then persist to long‑term storage asynchronously in background workers. This ensures user latency is not increased.
- Write events in append‑only fashion. Batch and retry durable writes to the warehouse/observability store (e.g., Langsmith / data warehouse).
- Use idempotency keys for each event so retries don’t create duplicates.

2) Core tables/events to store (structured, replayable)
- Conversation (one row per conversation)
  - conversation_id (primary key)
  - user_id
  - session_id
  - started_at (timestamp)
  - finished_at (timestamp, nullable)
  - metadata (JSON) — channel, bot_version, deployment_id, etc.
  - contains_pii (boolean)

- Turn (one row per turn/message)
  - conversation_id (FK)
  - turn_id (unique)
  - turn_index (int) — sequence within conversation
  - timestamp
  - role (user | bot | system)
  - text (redacted or full depending on PII policy)
  - raw_payload (JSON) — full message, embeddings, model outputs, intent, confidence, etc.
  - latency_ms (optional) — time to generate reply
  - succeeded (boolean)
  - parent_turn_id (nullable) — for threaded turns

- User (profile / lookup)
  - user_id (primary key)
  - anonymous_id (if anonymized)
  - created_at
  - user_metadata (JSON)

- Session (optional)
  - session_id (primary key)
  - user_id
  - started_at
  - ended_at
  - session_metadata (JSON)

- LateSignals (attachable late events)
  - signal_id (primary key)
  - conversation_id (FK)
  - turn_id (nullable) — attach to a particular turn when known
  - signal_type (escalation | email_reply | refund | satisfaction_score | etc.)
  - source (email | support_ticket | manual_audit | external_system)
  - signal_timestamp
  - details (JSON)
  - recorded_at

3) How to support late‑signal attachment
- Ensure every external signal includes the conversation_id (or a mapping step to find it).
- Store LateSignals as separate rows referencing conversation_id and optionally turn_id.
- Allow backfill jobs: accept signals at any time and link them to the existing conversation record; update conversation/turn metadata (e.g., escalation=true) without blocking runtime.
- Keep a change history (append events) so you can replay conversation + all late signals.

4) Queryability and durability
- Persist structured rows/JSON to a durable store or data warehouse/observability tool (Langsmith style). The record must be queryable by conversation_id, user_id, session_id, timestamps and signal_type.
- Index on conversation_id, user_id, session_id, and signal_timestamp for fast lookups.
- Store events long‑term and make them fetchable for replay, audits, and model evaluation.

5) PII handling (policy + schema support)
- Detection: flag PII at capture time where possible (contains_pii = true) and in turn.rows (pii_fields list).
- Redaction/storage:
  - Default: store redacted_text in the main logs used for querying/replay.
  - If raw PII must be retained, store it separately encrypted, with strict access controls and audit logs. Do not keep raw PII in the main queryable dataset.
- Access control & auditing: log any access to raw PII (who/when/why).
- Retention & deletion: implement retention policies and the ability to delete or purge raw PII mapped by conversation_id/session_id; keep an audit trail of deletions.
- If PII is lost, use your logs (conversation_id, turn_id, timestamps, contains_pii flag) to determine scope and evaluate impact.

6) Minimal fields required for replay and evaluation
- conversation_id, turn_id, turn_index, user_id, session_id, timestamp, text (or redacted_text), role, raw_payload (optional), contains_pii.
- For late events: signal_id, conversation_id, turn_id, signal_type, signal_timestamp, details.

7) Operational notes (keeps system non‑blocking and reliable)
- Emit events synchronously to a local buffer; persist asynchronously to durable store.
- Batch uploads and retries; keep local durable retry queue if remote store is unavailable.
- Keep events idempotent and append‑only so replay is deterministic.
- Make schema extensible via JSON metadata so new signals/fields can be added without breaking queries.
